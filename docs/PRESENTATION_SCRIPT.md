## Слайд 2 — Актуальность
**Говорит: Фомин Владимир**

Почему вообще стоит делать собственный интернет-магазин одежды — давайте разберёмся с цифрами.

По данным аналитического агентства Data Insight, объём российского рынка онлайн-торговли одеждой и обувью в 2024 году превысил **1,5 триллиона рублей**. Это не весь e-commerce — только одежда и обувь. И этот рынок растёт примерно на **25% ежегодно**: пандемия резко ускорила переход покупателей в онлайн, и этот тренд не разворачивается.

Казалось бы — выходи на маркетплейс и зарабатывай. Но здесь начинаются проблемы. Wildberries и Lamoda — крупнейшие площадки — удерживают комиссию от **15 до 25%** с каждой продажи. Это значит, что с товара за 5 000 рублей бренд получает максимум 4 250, а часто меньше — с учётом логистики, хранения и штрафов за возвраты. Помимо денег: маркетплейс диктует, как выглядит карточка товара, какой алгоритм её показывает, и — самое важное — **данные о покупателях остаются у маркетплейса**. Бренд не знает, кто его клиент, не может написать ему письмо, не может выстроить программу лояльности.

Конструкторы вроде Shopify или Tilda решают часть проблем — нет комиссии с продаж, есть своя витрина. Но как только нужна нестандартная логика — своя система скидок, интеграция с CRM, кастомный расчёт доставки — упираешься в стену. Shopify берёт абонентскую плату от $29 в месяц и закрывает доступ к серверной части. Tilda вообще не предназначена для полноценной торговли.

Наш проект «Atelier» демонстрирует третий путь: собственная платформа, разработанная небольшой командой с современным технологическим стеком. Полный контроль над витриной, над данными, над логикой. Без комиссий, без ограничений конструктора.

## Слайд 3 — Анализ аналогов
**Говорит: Фомин Владимир**

Перед тем как писать первую строчку кода, мы проанализировали существующие решения — чтобы понять, от чего отталкиваемся и что именно делаем лучше.

**Первая категория — крупные маркетплейсы: Wildberries и Lamoda.**

Их главное преимущество — готовая аудитория. Миллионы покупателей уже там, не нужно тратить бюджет на привлечение трафика. Плюс логистика: склады, курьеры, возвраты — всё берёт на себя площадка. Но цена за это высокая. Комиссия 15–25% съедает маржу. Карточка товара выглядит так, как требует маркетплейс, а не так, как хочет бренд. Алгоритм выдачи непрозрачен — сегодня твой товар в топе, завтра его никто не видит. И ключевое: данные покупателей — кто купил, когда, что ещё смотрел — остаются у маркетплейса. Бренду они не передаются.

**Вторая категория — конструкторы: Shopify, Tilda + Эквид.**

Это золотая середина для малого бизнеса без разработчиков. Быстрый старт, красивые шаблоны, встроенный приём платежей. Shopify — международный стандарт, мощная экосистема плагинов. Но: ежемесячная плата от $29, а за расширенные функции — от $79. Любая кастомизация бэкенда невозможна — сервер закрыт. Все данные хранятся на серверах Shopify. При закрытии аккаунта — теряешь всё.

**Третья категория — монобрендовые платформы: Zara, H&M.**

Полный контроль над UX, собственная CRM, программы лояльности. Но это разработка выделенной командой из десятков людей на протяжении лет. Для учебного проекта нереалистично, для небольшого бренда — финансово недостижимо.

**Вывод.** «Atelier» берёт лучшее от третьей категории — полный контроль и собственный бэкенд — но реализован маленькой командой за ограниченное время благодаря правильному выбору технологий. В таблице на слайде видно: мы единственные, у кого одновременно нет комиссии, есть полная кастомизация, полный доступ к данным клиентов и собственный бэкенд.

## Слайд 4 — Технологический стек
**Говорит: Демидов Максим**

Стек проекта разделён на три слоя: фронтенд, бэкенд и инфраструктура. Всего — 14 технологий.

**Фронтенд.** React 19 — актуальная мажорная версия с улучшенным механизмом рендеринга. TypeScript в строгом режиме — всё типизировано, включая ответы API и пропсы компонентов. Tailwind CSS версии 4 — утилитарная стилизация, адаптивная вёрстка без написания CSS вручную. React Router версии 7 — клиентская маршрутизация с защищёнными маршрутами. Vite — сборщик нового поколения, мгновенный старт и горячая перезагрузка при разработке.

**Бэкенд.** FastAPI на Python 3.12 — один из самых быстрых Python-фреймворков с встроенной валидацией через Pydantic и автоматической Swagger-документацией. SQLAlchemy 2 — ORM с современной декларативной типизацией моделей. Alembic — версионные миграции схемы базы данных. PostgreSQL — надёжная реляционная СУБД. JWT через python-jose и bcrypt через passlib — аутентификация и безопасное хранение паролей.

**Инфраструктура.** Docker Compose оркестрирует три независимых контейнера. nginx выступает реверс-прокси и отдаёт статику. Healthcheck в Compose гарантирует, что бэкенд не стартует раньше базы данных.

## Слайд 5 — Архитектура
**Говорит: Демидов Максим**

Архитектура — классическая клиент-серверная, трёхзвенная.

Поток запроса выглядит так: пользователь открывает браузер — запрос попадает на nginx на порту 80. nginx смотрит на путь: если он начинается с `/api/` — запрос проксируется на FastAPI, который слушает порт 8000 внутри Docker-сети. Любой другой путь — nginx отдаёт статику собранного React-приложения. FastAPI при необходимости идёт в PostgreSQL на порту 5432.

Бэкенд внутри организован строго по четырём слоям. Routes принимают HTTP-запрос и валидируют данные через Pydantic-схемы — если данные не соответствуют схеме, клиент сразу получает понятную ошибку. Services содержат бизнес-логику: расчёт итоговой цены с учётом скидки, оформление заказа с одновременной очисткой корзины, проверка прав доступа по роли. Repositories — изолированная работа с базой данных через SQLAlchemy, никакого SQL в других слоях. Models — декларативные ORM-модели, 10 таблиц.

Аутентификация через пару токенов. Access Token живёт 30 минут — передаётся в каждом запросе в заголовке `Authorization: Bearer`. Когда он истекает, фронтенд автоматически и незаметно для пользователя запрашивает новый через Refresh Token, который живёт 30 дней. При каждом использовании Refresh Token ротируется — старый сразу удаляется из базы, выдаётся новый. Это защита от кражи токена: украденный устаревший токен не сработает.

### Фомин Владимир — Фронтенд

Перейдём к живой демонстрации. Начну с клиентской части.

Фронтенд — это **Single Page Application** на React 19. Всего в приложении **9 страниц** и **33 TypeScript-файла**. Расскажу про каждый экран по порядку.

**Главная страница.** При открытии сайта пользователь видит Hero-баннер и слайдер с новинками. Слайдер не захардкожен — он делает реальный запрос к API с фильтром `is_new=true&limit=10` и показывает актуальные данные из базы. Никакого мока, никакого localStorage — чистый API.

**Каталог.** Это сердце магазина. Боковая панель с фильтрами: пол — мужское, женское, унисекс; категория товара; чекбокс «только новинки»; текстовый поиск. Все фильтры работают через URL query-параметры — это значит, что результат фильтрации можно скопировать из адресной строки и поделиться ссылкой, которая откроется с теми же фильтрами. Пагинация — данные загружаются постранично, не всё сразу. При изменении любого фильтра страница сбрасывается в начало. Авторизованный пользователь может добавлять товары в избранное прямо из каталога, не заходя в карточку.

**Карточка товара.** Открывается по URL `/catalog/{id}`. Загружает полную информацию о товаре: изображение, бренд, категорию, описание, размеры с наличием на складе. Если размера нет в наличии — кнопка выбора этого размера заблокирована, добавить в корзину невозможно. Кнопка «в корзину» и кнопка «в избранное» требуют авторизации — неавторизованный пользователь перенаправляется на страницу входа.

**Корзина.** Полноценное управление: увеличить и уменьшить количество каждой позиции, удалить отдельный товар, очистить корзину целиком. Внизу — поле ввода адреса доставки и итоговая сумма. После нажатия «Оформить заказ» на сервере в одной транзакции создаётся заказ и очищается корзина. Пользователь видит подтверждение.

**Профиль и история заказов.** В личном кабинете пользователь видит свои данные, может изменить имя прямо на странице, и видит историю всех заказов с текущим статусом — ожидает обработки, в доставке, выполнен.

**Авторизация.** Две формы — вход и регистрация. После входа токены сохраняются, и все последующие запросы к защищённым эндпоинтам идут с заголовком Bearer. При истечении токена клиент автоматически обновляет его через refresh — пользователь этого не замечает.

**Административная панель.** Доступна только пользователям с ролью `admin`. Три вкладки: управление товарами — можно изменить наличие, скидку, новинку или удалить товар; управление пользователями — смена роли между `client` и `admin`; управление заказами — смена статуса через выпадающий список.

Отдельно отмечу: всё приложение адаптивно — работает как на десктопе, так и на мобильном. Хедер при прокрутке компактизируется — уменьшается в высоту с плавной анимацией.

### Рахманинов Савва — Бэкенд

Теперь я расскажу о серверной части.

Бэкенд написан на Python 3.12 с использованием FastAPI. В проекте **37 Python-файлов** и **29 REST API эндпоинтов**, организованных в **8 роутеров**.

Разберём каждый роутер:

- **`/api/auth`** — 5 эндпоинтов: регистрация, вход, обновление токена, выход и получение текущего пользователя. Пароли хэшируются bcrypt с автоматической солью — даже если база утечёт, пароли не будут скомпрометированы в открытом виде.
- **`/api/products`** — 5 эндпоинтов: получение списка с пагинацией и фильтрами, получение одного товара, создание, обновление и мягкое удаление. Мягкое удаление — это важно: товар не стирается из базы, просто получает флаг `is_active=false`. История заказов с этим товаром сохраняется.
- **`/api/categories`** — 2 эндпоинта: список категорий и создание новой (только администратор).
- **`/api/cart`** — 5 эндпоинтов: получить корзину, добавить позицию, изменить количество, удалить позицию, очистить всю корзину.
- **`/api/favorites`** — 3 эндпоинта: список избранного, добавить товар, убрать товар.
- **`/api/orders`** — 3 эндпоинта: история заказов, один заказ, оформление заказа.
- **`/api/users`** — 2 эндпоинта: профиль текущего пользователя и его обновление.
- **`/api/admin`** — 4 эндпоинта: список всех пользователей, смена роли, список всех заказов, смена статуса заказа. Каждый защищён зависимостью `require_admin` — если роль не `admin`, запрос отклоняется с кодом 403.

Покажу ключевой сценарий — оформление заказа, `POST /api/orders/checkout`. Эндпоинт делает следующее в одной транзакции: читает все позиции корзины пользователя, для каждой позиции фиксирует цену на момент заказа — это важно, цена могла измениться позже, — создаёт запись заказа и все позиции, затем очищает корзину. Если в любом месте возникает исключение — вызывается `db.rollback()`, и данные остаются консистентными. Пользователь либо получает оформленный заказ, либо корзина остаётся нетронутой.

База данных — **10 таблиц**: `users`, `refresh_tokens`, `categories`, `products`, `product_images`, `product_sizes`, `cart_items`, `favorites`, `orders`, `order_items`. Все связи объявлены через `ForeignKey` с каскадным удалением там, где это логично.

На правом скриншоте — логи Docker в реальном времени. Три контейнера работают параллельно: `atelier-db`, `atelier-backend`, `atelier-frontend`. Бэкенд не стартует пока база данных не пройдёт healthcheck — это настроено через `depends_on: condition: service_healthy` в docker-compose. При первом запуске автоматически выполняется Alembic-миграция — создаются все 10 таблиц — затем seed-скрипт заполняет базу тестовыми данными: 2 пользователя, 6 категорий, 11 товаров с размерами и изображениями. При повторном запуске seed проверяет, есть ли уже данные, и пропускает заполнение.

## Слайд 7 — Будущие улучшения
**Говорит: Круцяк Глеб**

В ходе тестирования системы я зафиксировал области, которые логично развивать в следующих итерациях. Разделю на два направления — функциональные и технические.

**Функциональные улучшения.**

Первое — галерея изображений. Сейчас у каждого товара одно фото. Для интернет-магазина одежды это критичный недостаток: покупатель хочет видеть вещь с разных ракурсов, на модели и в деталях. Модель данных уже позволяет хранить несколько изображений — таблица `product_images` есть — но фронтенд показывает только первичное.

Второе — отзывы и рейтинги. Без пользовательских оценок покупателю сложно принять решение. Нужна отдельная таблица отзывов, связанная с пользователем и товаром, и отображение среднего рейтинга на карточке.

Третье — промокоды и программа лояльности. Маркетинговый инструмент, критичный для удержания клиентов. На уровне бэкенда — отдельная таблица промокодов с типом скидки, сроком действия и лимитом использований.

Четвёртое — уведомления о статусе заказа. Сейчас администратор меняет статус, но покупатель узнаёт об этом только зайдя в профиль. Нужна интеграция с email или мессенджером — письмо «Ваш заказ передан в доставку».

**Технические улучшения.**

Первое — автотесты. Бэкенд не покрыт тестами. При дальнейшем развитии это риск: изменение одного сервиса может сломать другой, и это обнаружится только в продакшене. Нужен pytest с тестами для каждого сервисного слоя и интеграционные тесты для ключевых сценариев — регистрация, оформление заказа, смена статуса.

Второе — кэширование через Redis. Каждый запрос каталога сейчас идёт в PostgreSQL. Список категорий и популярные фильтры меняются редко — их можно кэшировать в Redis на несколько минут, снизив нагрузку на базу.

Третье — CI/CD пайплайн. Сейчас деплой ручной: запустил команду, подождал. Нужен GitHub Actions: при каждом пуше — автоматическая сборка, прогон тестов, и деплой если всё прошло.

Четвёртое — S3-хранилище для изображений. Сейчас фотографии товаров лежат в статике контейнера. При масштабировании или пересборке образа они исчезают. Нужно вынести в объектное хранилище — MinIO для self-hosted или AWS S3.

Пятое — аналитический дашборд. Администратор сейчас видит только список заказов. Нужны графики: выручка по дням, топ товаров, конверсия из просмотра в покупку — это основа для принятия бизнес-решений.

Итого: **4 функциональных** и **5 технических** инициативы для следующего релиза.
